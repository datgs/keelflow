# Execution Plan: Batch-insert bulk chunk jobs into Chancy

Date: 2026-11-23

## Status

Completed 2026-11-23 — candidate **rejected after measurement**. A direct
set-based kernel insert was implemented, proven correct (row contract,
notification, rollback, schema guard), then benchmarked: it saved only
~1.3s of `parent_super_run_s` at 1M rows (~8%), not the ~17s the v5
attribution implied. The real super_run cost is the partition CTE's
1M-row claim+UPDATE, not kernel round-trips. User chose to keep the
upstream `push_many_ex` API rather than own kernel-table coupling for a
marginal gain. Reverted; plan retained for evidence.

## Outcome

Reduce bulk-parent fan-out overhead by inserting Chancy kernel jobs in a
set-based operation, only if it preserves the current Chancy push contract and
measured performance improves. Engine job rows, kernel job rows, chunk rows,
row assignments, staging writes, and parent completion must remain in the same
transaction. If correctness, compatibility, or a useful performance gain is not
proven, keep `kernel.push_many_ex`.

## Context and verified evidence

- The completed benchmark plan records the 1M-row v5 result: about 17 seconds
  remain in `parent_super_run_s`, with kernel-row insertion identified as the
  remaining per-job insert cost (`docs/plans/completed/bulk-partition-optimization.md:287-324`).
- Bulk fan-out creates engine child rows with one set-based INSERT, then calls
  `kernel.push_many_ex(cur, kernel_jobs)` in the same dispatch transaction
  (`src/keelflow/engine/bulk.py:224-255`).
- Chancy is locked to 0.26.0 in `uv.lock`; `pyproject.toml` currently permits
  `chancy>=0.26.0` without an upper bound.
- In installed Chancy 0.26.0, `push_many_ex` sorts by unique-key lock order,
  calls `_push_job_sql()` once per job, and emits one `queue.pushed`
  notification per used queue when notifications are enabled
  (`chancy/app.py:672-712`, `:1400-1435`, `:1534-1575`).
- The kernel row insert contract includes `id`, `queue`, `func`, `kwargs`,
  `limits`, `meta`, `priority`, `max_attempts`, `scheduled_at`, and
  `unique_key`. The current bulk chunk jobs use the default queue, the engine
  dispatch function, `job_id` kwargs, chunk metadata, max attempts 3, no limits,
  default priority, no unique key, and a creation-time schedule
  (`src/keelflow/engine/bulk.py:758-775`).
- The previous completed plan explicitly excluded direct writes to Chancy-owned
  tables pending separate design (`docs/plans/completed/bulk-partition-optimization.md:121-146`).
  This follow-up supplies that design; it does not authorize implementation by
  itself.
- `spec/04-bulk.md` requires staging, partitioning, chunk enqueue, and parent
  completion to commit atomically (`spec/04-bulk.md:7-17`).

## Scope

In scope:

- Validate the current kernel-row and notification behavior against the
  Chancy version actually resolved by the lockfile.
- Replace per-job kernel inserts for bulk chunk fan-out with a set-based insert
  only if the compatibility and correctness proofs pass.
- Add tests for the inserted kernel row contract, transaction rollback,
  notification semantics, and normal recovery/claim execution.
- Measure before/after using the existing isolated benchmark protocol and exact
  correctness oracle.

Out of scope:

- Changing Chancy itself, sending an upstream patch, or monkey-patching its
  APIs.
- Direct kernel-table writes for non-bulk enqueue paths.
- Changing chunk IDs, retry budgets, dispatch kwargs, cancellation, fan-in,
  unique-key semantics, or transaction boundaries.
- Claiming a fixed speedup before benchmark evidence.
- Raising or narrowing the supported Chancy version range without a separate
  compatibility decision supported by evidence.

## Approach and contracts

The implementation candidate is a bulk-specific set-based INSERT to the
kernel jobs table, using the active Chancy prefix and the caller's cursor. This
is not accepted by default: Task 1 must verify that each compatibility claim
below is supported before Task 2 may write kernel-owned rows directly.

Preserve these contracts:

1. **Identity:** every kernel job gets a Chancy-compatible UUID generated
   independently from the corresponding engine job ID, as the current
   `push_many_ex` path does. Do not copy the engine child ID into the kernel
   table. Use a supported ID-generation API if available; otherwise verify the
   required ID representation and record the compatibility limit.
2. **Row values:** preserve the effective values generated by the existing
   Chancy `Job` + `_get_job_params` path: queue, dispatch function, kwargs,
   limits, metadata, priority, max attempts, schedule time, and `unique_key`
   (NULL for these chunk jobs). Tests compare persisted rows to the current
   API's expected parameterization, not just to a hard-coded count.
3. **Uniqueness and locks:** chunk jobs currently have no `unique_key`; prove
   that this remains true. Do not generalize the direct-write path to keyed
   jobs. If any candidate row gains a key, retain Chancy's lock ordering and
   conflict behavior by using its API instead.
4. **Notifications:** when `kernel.notifications` is enabled and at least one
   chunk job is inserted, send one `queue.pushed` notification for the default
   queue through the Chancy notification method, on the same cursor and
   transaction. Send none when notifications are disabled or there are no
   chunk jobs. Do not hand-build PostgreSQL `NOTIFY` payloads.
5. **Atomicity:** engine child rows and kernel jobs remain in the same caller
   transaction. Any failure rolls back both; no manual commit is introduced.
6. **Compatibility:** use the active kernel's configured table prefix and safe
   SQL identifiers. Document the Chancy schema contract being relied on. Since
   the declared dependency has no upper bound, tests must make unsupported
   schema/API changes fail visibly. Do not silently claim all future Chancy
   versions are compatible; if evidence requires a supported-version bound,
   stop and request a separate dependency-policy decision.

## Tasks

### Task 1 — Confirm the Chancy compatibility boundary

- **Goal:** Establish whether a bulk-specific direct insert is safe for the
  currently supported dependency range.
- **Required outcomes:** Inspect the Chancy 0.26.0 lock-resolved insert schema,
  ID generator, defaults, notification API, prefix behavior, and unique-key
  handling. Identify whether those APIs are stable/public or implementation
  details. Decide whether the candidate can proceed without changing the
  declared dependency range; otherwise stop with the evidence and a concrete
  compatibility decision for the user.
- **Constraints:** No product code edits and no broad dependency update.
- **Acceptance evidence:** A concise compatibility matrix tied to installed
  Chancy 0.26.0 source and tests; all current bulk chunk job fields mapped to
  the existing Chancy insertion behavior; any unsupported-version question is
  explicit, not assumed away.
- **Verification:** Inspect lockfile-resolved source and existing project
  tests; no service or data mutation required.
- **Ownership:** Chancy dependency contract and this plan.
- **Dependencies:** None.

### Task 2 — Implement set-based fan-out behind the verified contract

- **Goal:** Replace per-job kernel inserts for bulk chunks only, retaining the
  existing external behavior and transaction.
- **Required outcomes:** Generate independent kernel IDs; insert every required
  kernel field with values equivalent to the current `push_many_ex` path; use
  active prefix and the same cursor; notify via Chancy's notification API
  under the conditions above. Keep non-bulk callers on Chancy's push API.
- **Constraints:** No direct commit, no unique-key rows, no altered retry or
  scheduling behavior, and no use of engine IDs as kernel IDs.
- **Acceptance evidence:** Database-backed tests verify exact engine/kernel
  membership and mapped fields, default queue/dispatch metadata, UUID
  independence, `unique_key IS NULL`, enabled/disabled notification behavior,
  and full rollback when the bulk insert or subsequent transaction work fails.
- **Verification:** `uv run pytest tests/test_bulk.py -q`; add/extend focused
  tests in that suite. Also run the relevant e2e claim/recovery test.
- **Ownership:** `src/keelflow/engine/bulk.py`, `tests/test_bulk.py`.
- **Dependencies:** Task 1 approved compatibility contract.

### Task 3 — Prove end-to-end behavior and benchmark

- **Goal:** Verify the kernel claims and executes set-inserted jobs normally and
  determine whether the change earns its complexity.
- **Required outcomes:** Run the existing exact output oracle and full relevant
  bulk lifecycle; compare before/after with the same isolated benchmark
  protocol, environment, worker count, chunk size, and correctness checks.
  Report run count, spread, `parent_super_run_s`, parent transaction duration,
  total wall time, and any available lock/WAL indicators. Treat a sub-second
  `parent_super_run_s` as a hypothesis to test, not an acceptance threshold.
- **Constraints:** No concurrent benchmark/soak owner; do not weaken or bypass
  the exact oracle. If there is no repeatable improvement or any contract
  regression, revert the candidate and retain `push_many_ex`.
- **Acceptance evidence:** Every measured run passes the exact oracle; kernel
  jobs are claimed and complete; before/after artifacts identify configuration
  and timing definitions; result records either a repeatable improvement or a
  reason to retain the old path.
- **Verification:** Focused PostgreSQL bulk tests, relevant e2e test, repository
  required checks (`uv run pytest -q`, `uv run ruff check src examples tests`,
  `uv run mypy src/keelflow`, `git diff --check`), then 500k/1M benchmark if
  lower-scale evidence is sound.
- **Ownership:** bulk benchmark artifacts and validation record.
- **Dependencies:** Task 2.

## Risks and recovery

- **Kernel schema/API drift (high):** direct writes bypass Chancy's insertion
  method. Mitigate with explicit field mapping, a 0.26.0 compatibility test,
  prefix-safe identifiers, and visible failure when expected schema is absent.
  If the declared version range cannot be supported honestly, stop before
  implementation and ask whether to narrow it or retain Chancy's API.
- **Semantic mismatch (high):** missing/defaulted kernel fields may cause
  dispatch, retries, scheduling, or plugins to behave differently. Compare
  persisted rows and prove claim/retry/recovery through real workers.
- **Notification loss or duplication (medium):** call the Chancy notify method
  once per non-empty batch in the same transaction; test enabled and disabled
  cases and confirm notification is committed only with the rows.
- **Partial/orphaned enqueue (high):** prove rollback of engine and kernel rows
  together; do not split or commit the existing dispatch transaction.
- **No actual performance gain (medium):** require corrected phase and total
  timing evidence; revert the extra coupling if it does not repeatably improve
  the target workload.

Recovery is a code rollback to `kernel.push_many_ex`; no migration or persistent
schema change is planned. Any benchmark data created by local runs must use the
existing isolated benchmark scope and cleanup contract.

## Task 1 compatibility evidence (2026-11-23)

Chancy `0.26.0` is lockfile-resolved (`uv.lock:234-236`) and installed at
`.venv/lib/python3.12/site-packages/chancy`. The public `chancy.Job` contract
and public `Chancy.notify_many` API are sufficient; only `{prefix}jobs` table
shape is relied on beyond the public API.

| Contract point | Verified Chancy 0.26.0 behavior | Compatibility decision |
|---|---|---|
| ID | `_get_job_params` returns `chancy_uuid()`; `chancy.utils.chancy_uuid()` is importable and generates UUID7-compatible IDs | Generate each kernel ID via `chancy_uuid()`, independently of the engine job ID. |
| Row fields | `_push_job_sql` inserts `id, queue, func, kwargs, limits, meta, priority, max_attempts, scheduled_at, unique_key`; the migration gives `state='pending'`, `attempts=0`, `taken_by NULL`, `errors='[]'` defaults | Insert the same fields with equivalent values; omit `unique_key` so it remains NULL. |
| Bulk chunk values | `DEFAULT_QUEUE`, `DISPATCH_FUNC`, `{"job_id": str(engine_child_id)}` kwargs, `[]` limits, chunk metadata, `priority=0`, `max_attempts=3`, generated-at-creation `scheduled_at`, `unique_key=None` | Preserve exactly; verify by querying the persisted row rather than assuming SQL defaults. |
| Unique keys/locks | `push_many_ex` sorts keyed jobs before locking (`_in_lock_order` / `lock_order_key`) | Bulk chunk jobs have no keys; direct batch is restricted to unkeyed rows only. |
| Notifications | With `kernel.notifications`, `push_many_ex` calls `notify(cursor, "queue.pushed", {"q": queue})` once per queue after insert | Call public `kernel.notify_many(cursor, [("queue.pushed", {"q": DEFAULT_QUEUE})])` once for a non-empty batch when notifications are enabled. |
| Prefix | `Chancy.prefix` is used to address `{prefix}jobs` and `{prefix}events` | Build the target table through `psycopg.sql.Identifier(f"{kernel.prefix}jobs")`; never interpolate the prefix as a value. |
| Transaction | `push_many_ex` writes on the supplied cursor and sends NOTIFY on the same cursor | Use the same `ctx.tx` cursor; no extra commit/connection. |
| Dependency range | `pyproject.toml` permits `chancy>=0.26.0`; lock and local environment resolve `0.26.0` | No range change in this implementation. Add a schema/API compatibility test so a future kernel shape fails visibly; document that support beyond the checked schema is not implied. |

## Result (2026-11-23)

Implemented behind the Task-1 compatibility matrix, then **rejected after
measurement** and reverted to `kernel.push_many_ex` (user decision).

Benchmark, same box/DSN, `keelflow-batch`, chunk=1000, w8, 2 reps,
exact oracle green on every run:

| rows | baseline `super_run` | set-based `super_run` | delta |
|---|---|---|---|
| 500k | 7.25–7.42s | 6.07–7.05s | ~−1.0s |
| 1M   | 16.1–18.3s | 15.2–16.6s | ~−1.4s |

The v5 "kernel-row inserts are the remaining ~17s of `super_run`"
attribution was wrong: kernel INSERTs cost ~1.3s/1M. The dominant cost
is the partition CTE's 1M-row claim + `chunk_id` UPDATE + chunk/engine
INSERTs (WAL + row writes, not round-trips). A ~1.3s/1M gain does not
justify permanent coupling to Chancy's internal jobs-table schema,
especially since the path is not extensible (unkeyed-only; a future
unique-key chunk push would need Chancy's conflict/lock-order logic
re-implemented). Correct upstream path is an `executemany` patch to
`push_many_ex`, not an engine-side direct write.

Proof run before revert: 209 tests pass (28/28 in `test_bulk.py`
including the 4 contract tests), ruff + mypy clean.
Artifacts: `.spikes/erp_bulk_bench/result_{baseline,batchinsert}_{500k,1m}.{json,md}`.
